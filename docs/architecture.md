# Архитектура MiniDb

## Поток запроса

`Program → SqlScript → Lexer → Parser → Statement (AST) → Database → QueryResult`.

- `Sql.cs`: лексер хранит текст, признак строкового литерала и позицию токена. Парсер рекурсивного спуска строит records: CreateTable, Insert, Select, Update, Delete, CreateIndex, Transaction. Уровни `Or → And → Atom → Operand` обеспечивают приоритеты.
- `Engine.cs`: проверка схемы, типов и имён, исполнение, группировка, сортировка. Фильтр SELECT связывает имена с позициями один раз и компилируется в делегат, чтобы не разрешать имена на каждой строке. Это одинаково для индексного и последовательного пути.
- `BTree.cs`: собственное B-дерево минимальной степени 16, бинарный поиск внутри узла, split полного дочернего узла до спуска. В узле максимум 31 различный ключ, минимум 15 (кроме корня). У одинакового ключа список rowId. Ключи и значения хранятся как во внутренних узлах, так и в листьях. Высота для 2000 ключей проверяется тестом.
- `Storage.cs`: кодирование записей через Span и BinaryPrimitives, упаковка в страницы, чтение схемы/строк/топологии индексов.
- `WalStore.cs`: эксклюзивная блокировка, durable commit, checkpoint и recovery. Подробный порядок fsync: [wal.md](wal.md).
- `DemoData.cs`: генератор и быстрый замер; `benchmarks/` — BenchmarkDotNet.

## Выполнение и атомарность

Таблица содержит схему, `Dictionary<long, object[]> Rows`, счётчик NextId и индексы. Первый ключ словаря — внутренний rowId, он не равен PRIMARY KEY и не меняется при UPDATE. Сравнения INT/TEXT проверяются по схеме; строки сравниваются ordinal. PRIMARY KEY проверяется множеством уникальных значений. INSERT с несколькими строками выполняется как одна команда.

Перед изменяющим SQL делается копия состояния. При ошибке возвращается копия: частичный INSERT, нарушение PK или слишком большая строка не оставляют изменений. BEGIN удерживает отдельную копию для ROLLBACK; ошибка одного SQL не отменяет остальные успешные команды текущей транзакции. После изменения B-деревья перестраиваются из текущих строк. Это упрощает корректное удаление и обновление, но имеет цену O(n log n) на команду записи. Отдельный алгоритм B-tree delete не заявляется. Снимок разделяет старые деревья безопасно: перестройка заменяет Tree новым объектом, не мутирует сохранённый.

Оптимизатор SELECT выбирает equality-условие `column = literal`, в том числе внутри AND. Если есть индекс, `Tree.Find` выполняет O(log n + k), затем прямые обращения к Rows по rowId, и остаточный фильтр проверяет кандидатов. OR не сужается одним индексом, иначе потерялись бы строки другой ветви. Индекс на диапазон не применяется. EXPLAIN вызывает тот же ChooseIndex; ForceFullScan — диагностический переключатель для честного сравнения. LastRowsExamined позволяет тесту отличить seek от скрытого полного перебора.

JOIN — вложенные циклы по двум таблицам с проверкой равенства ON. Полная схема содержит table.column; неквалифицированное имя допускается только при единственном совпадении. Затем выполняются WHERE, GROUP BY/агрегаты либо проекция, ORDER BY, LIMIT. Физического индексного join нет.

## Бинарные страницы и адресация

Все числа little endian. Файл кратен 4096 байтам.

| Место | Формат |
| --- | --- |
| Страница 0 | ASCII `MINIDB01` (8 байт), остальное зарезервировано и заполнено нулями |
| Обычная страница | uint16 used (включает эти 2 байта), затем записи; остаток — нули |
| Запись на странице | uint16 длина payload, затем payload |
| Целое в payload | int64 LE |
| Строка в payload | int64 длина UTF-8 в байтах, затем UTF-8 |
| Значение | int64 tag: 0 для INT + int64, 1 для TEXT + строка |

Тип payload определяется первым int64:

1. Схема: type=1, имя таблицы, NextId, количество столбцов, затем для каждого имя, тип, признак PK.
2. Строка: type=2, имя таблицы, rowId, значения по порядку схемы.
3. Индекс: type=3, имя таблицы, имя индекса, номер столбца (с нуля).
4. Фрагмент дерева: type=4, имя таблицы, имя индекса, бинарные байты фрагмента (до 3000).

Топология дерева сериализуется рекурсивно: leaf:int64, число ключей:int64; для каждого ключ (Value), размер bucket:int64 и rowId:int64; затем дочерние узлы (keys+1, если не лист). Фрагменты склеиваются в порядке записи, восстанавливается сама топология, без сканирования таблицы и повторного построения дерева.

Физический адрес записи — `(номер страницы, смещение длины записи)`, где номер страницы начинается с нуля. Запись никогда не пересекает границу страницы. Стабильный логический адрес строки — `(таблица, rowId)`. Индекс хранит этот логический адрес. При открытии файла восстанавливается отображение rowId → массив значений в RAM; SELECT по индексу читает словарь напрямую. Это сознательная модель in-memory исполнения поверх бинарного страничного checkpoint, не буферный пул дисковых страниц.

Максимум payload — 4092 байта: 4096 минус used и длина записи. Служебные поля строки и имя таблицы входят в лимит, поэтому допустимый TEXT меньше 4092 и зависит от остальной строки. Проверка производится по реальному сериализованному UTF-8, не по количеству символов. Схема тоже должна помещаться; не более 256 столбцов. Большие деревья разбиваются на фрагменты, bucket дубликатов может занимать много страниц. При UPDATE и DELETE полный новый образ перепаковывается, удалённые строки не записываются; rowId оставшихся строк сохраняются, освобождённые номера повторно не используются.

## Транзакции и восстановление

No-steal: неподтверждённое состояние находится только в памяти; до durable COMMIT основной файл не меняется. WAL содержит полный образ страниц с SHA-256 и завершающим commit marker. fsync тела предшествует fsync маркера; checkpoint и fsync файла базы предшествуют очистке WAL. Поэтому ошибка/авария во время checkpoint восстанавливается из WAL, а неподтверждённый frame не применяется.

Recovery запускается до чтения основного файла: это позволяет восстановить частично перезаписанный checkpoint. Восстановление идемпотентно, поскольку повторно пишет один и тот же образ, а не исполняет SQL. Повреждённый/неполный хвост останавливает чтение. После I/O-ошибки объект базы блокирует дальнейшие SQL до закрытия/повторного открытия. Доступ одного писателя обеспечивается FileShare.None на отдельном `.lock` файле; сам файл может остаться после выхода, это не означает активную блокировку.

Тестовый процесс может остановиться в точках uncommitted, wal-body, before-commit, after-commit, checkpoint. Родитель ждёт файл-сигнал и вызывает настоящее Kill(true), затем проверяет старые/новые данные, индекс и повторное открытие. Наличие сигнала означает достигнутую точку протокола, а не произвольную задержку.

## Практические границы

Ограничения и точные команды находятся в README. Полный образ в WAL и полная перестройка индексов выбраны ради проверяемой корректности учебного проекта. Для промышленной базы следующие шаги были бы: buffer pool, изменяемые дисковые страницы, инкрементальное обслуживание индексов, page-LSN, конкурентность и MVCC. Эти бонусные задачи не реализованы.
