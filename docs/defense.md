# Подготовка к защите

## Как рассказать проект за 2–3 минуты

MiniDb — консольная база на C#/.NET 8. Сначала SQL превращается в токены, затем в дерево команд. Исполнитель проверяет схему, выполняет операцию и возвращает таблицу результата. Данные сохраняются своим бинарным форматом страниц 4096 байт. Для равенства есть собственное B-дерево. Явные транзакции держат изменения в памяти; COMMIT сохраняется через WAL с fsync. После аварии WAL автоматически восстанавливает подтверждённое состояние. JOIN сделан вложенными циклами.

## Термины и ответы

**Лексер** разбивает текст на слова, числа, строки, операторы и разделители. Например, `age >= 25` — три токена. Токен хранит позицию для понятной ошибки.

**Парсер** проверяет грамматику и строит AST (абстрактное синтаксическое дерево). Рекурсивный спуск — функции для уровней грамматики. Or вызывает And, поэтому AND связывает сильнее OR; скобки снова вызывают Or.

**Страница** — фиксированный блок 4096 байт. На странице есть занятая длина и записи с собственными длинами. Целая строка должна помещаться на одной странице. Строки — UTF-8, числа — little endian, доступ к байтам — Span/BinaryPrimitives.

**B-дерево** — сбалансированное дерево с несколькими ключами в узле. В MiniDb минимальная степень 16: до 31 ключа. Полный узел разбивается, медианный ключ переходит в родителя. Все листья на одной глубине. Одинаковые значения индексируемого столбца имеют bucket rowId. Топология сохраняется на диске. Поиск — O(log n + k).

**Индекс** связывает значение столбца с rowId. По `age=54321` дерево выдаёт один rowId, и исполнитель читает только эту строку из словаря. Full scan проверяет все 100000 строк. EXPLAIN использует тот же оптимизатор, что SELECT; тесты проверяют число просмотренных строк. Диапазоны и OR пока не оптимизируются.

**Транзакция** объединяет изменения: BEGIN начинает, COMMIT подтверждает, ROLLBACK отменяет. Ошибка одной команды откатывает эту команду. Вне BEGIN каждая команда изменения автоматически подтверждается. Одновременных пользователей нет.

**WAL** — журнал предзаписи. Сначала полное новое состояние записывается в журнал и fsync, затем commit marker и fsync. Только после этого переписывается база. WAL очищается после fsync базы. При аварии полный подтверждённый frame восстанавливается, оборванный хвост отбрасывается. Повторное восстановление не дублирует INSERT: переписываются страницы.

**Почему не JSON?** Файлы базы — бинарные страницы с типизированными записями, двоичными длинами, значениями и фрагментами дерева; JSON не используется.

**Что происходит при UPDATE/DELETE индекса?** После успешного SQL дерево перестраивается. Это корректно для дубликатов и отката, но медленнее инкрементального удаления. При ROLLBACK восстанавливается старый снимок данных и деревьев.

**Почему быстрый поиск в RAM считается корректным?** Сравниваются два пути одной открытой базы на одних данных. Таблица и дерево оба находятся в RAM; cold disk I/O не заявляется. Генерация, парсинг и построение индекса не входят в benchmark. Это явно описанное ограничение архитектуры.

## Порядок показа

1. `dotnet test -c Release`: показать пройденные тесты, особенно KillRealProcessAndRecover.
2. Запустить обязательный пример из README на новой базе; показать русский текст, фильтр и индексный EXPLAIN.
3. Показать ошибку повторного PK: программа продолжает работать.
4. Показать GROUP BY и JOIN примерами README.
5. Выполнить `scripts/defense.ps1`: 100000 строк, Full scan → индекс → seek, времена, убийство процесса до COMMIT, повторное открытие.
6. Объяснить, что при убийстве после fsync commit marker результат уже подтверждён; показать этот вариант или интеграционный тест.
7. Показать docs/benchmark.md. В облаке средние дали около 750×, это не обещание для любого ПК и любого запроса.

## Честно назвать ограничения

Все данные в RAM; один процесс; только INT/TEXT; строка ограничена страницей; один столбец ORDER BY; INNER JOIN двух таблиц; нет NULL/alias/подзапросов; индекс только для equality SELECT; перестройка деревьев и полный образ WAL делают записи дорогими. Это учебная, не промышленная СУБД.
