# Фактическое измерение поиска

Дата: 29 октября 2026. Команда из корня:

```powershell
dotnet run -c Release --project benchmarks/MiniDb.Benchmarks
```

100000 строк users: id=age=1..100000. Запрос один и тот же: `SELECT * FROM users WHERE age=54321`. GlobalSetup генерирует данные, строит индекс и проверяет равенство единственной строки результата. Измеряются Execute(один AST), выбор плана, фильтр и материализация результата, без парсинга, генерации, построения и диска. ForceFullScan переключает только доступность индекса в одном Database. Оба пути используют одинаковый скомпилированный фильтр. Индексный путь всё равно проверяет остаточное условие и получает строку по rowId.

Отношение средних 1842.930 / 2.456 ≈ **750.38×**. Порог 100× достигнут в этом прогоне. ShortRun: один запуск, три прогрева и три измерения; широкие 99.9% доверительные интервалы в колонке Error отражают малое число итераций и шум облачной машины. Это не статистическая гарантия минимального ускорения на любом компьютере. Для более стабильного отчёта можно увеличить число итераций в атрибуте benchmark.

Дополнительный быстрый замер полного сценария защиты: 6.502580 ms scan и 0.010108 ms index, 643.28×. Он включает менее прогретый JIT и другую методику (медиана семи серий), поэтому отличается от BenchmarkDotNet; основной результат — таблица выше. При низкой селективности, другой машине или запросе по диапазону такого ускорения ожидать нельзя. Диапазонные условия пока используют Full scan.

Сырые результаты создаются в игнорируемой BenchmarkDotNet.Artifacts, в git сохраняется только этот короткий фактический отчёт.
